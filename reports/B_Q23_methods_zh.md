## 1. 研究目标与问题边界

第 2 问研究在既定节点容量、型号约束和不可抢占条件下，如何决定等待作业的启动次序与 worker 放置。主要目标是降低全部作业平均等待、提高固定 90 天窗口的完成数量，同时检查长尾等待、不同作业群体、资源分配率和算法计算成本。不同目标可能冲突，因此不以某一个指标的胜出宣称全局最优。

第 3 问在相同调度基础上引入一种有限的跨型号机制：部分 A10 作业假定兼容 A100/A800，只在到达时尝试即时分流。研究它能否缓解原池排队，以及会给目标池的原生作业带来什么代价。

本文没有求解全局最优调度，也不声称所选规则最优。题面允许的运行时长已知，不等于允许预知未来到达；调度只能使用截至当前事件时刻已经提交的作业。第 3 问的兼容性和速度是新增情景假设，不能从第 1 问的工作量比例推断出来。

## 2. 统一建模与可行性约束

### 2.1 符号

| 符号 | 定义 |
|---|---|
| \(s_j,d_j\) | 作业 \(j\) 的提交时刻与原始运行时长，单位为秒 |
| \(g_j,c_j,m_j\) | 每个 worker 的 GPU 请求、vCPU 请求和 worker 数 |
| \(G_j=g_jm_j,\ C_j=c_jm_j\) | 整个作业的 GPU、vCPU 请求 |
| \(b_j,f_j\) | 作业实际启动与结束时刻 |
| \(G_n^{cap},C_n^{cap}\) | 节点 \(n\) 的物理 GPU、vCPU 容量 |
| \(y_{jn}\) | 作业 \(j\) 放在节点 \(n\) 上的 worker 数，取非负整数 |
| \(\mathcal A_j\) | 作业允许使用的 GPU 型号集合 |

第 2 问中，\(\mathcal A_j\) 只含原请求型号。第 3 问只有符合兼容性假设的 A10 作业才有额外允许型号，且一个作业的全部 worker 最终仍放在同一种 GPU 型号上，不混用型号。

### 2.2 时间与放置约束

全部节点在 \(t=0\) 空闲。时间零点提交的作业作为正常提交处理，不能当成先前已经开始运行的作业。

每个作业满足

\[
b_j\ge s_j,\qquad f_j=b_j+d_j^{exec},\qquad
\sum_n y_{jn}=m_j,
\]

其中第 2 问 \(d_j^{exec}=d_j\)，第 3 问的迁移时长见第 5 节。若节点型号不在 \(\mathcal A_j\) 中，则 \(y_{jn}=0\)。同一个 worker 的 CPU 和 GPU 由同一个 \(y_{jn}\) 同时占用，不能拆到两个节点。

对任意节点和时刻，必须满足

\[
\sum_j g_jy_{jn}\mathbf1\{b_j\le t<f_j\}\le G_n^{cap},
\qquad
\sum_j c_jy_{jn}\mathbf1\{b_j\le t<f_j\}\le C_n^{cap}.
\]

一次性提交全部 worker 的分配结果；只找到部分 worker 的位置时不能提前占用或启动。启动后 \(y_{jn}\) 在运行区间保持不变，不抢占、不迁移、不提前释放。占用采用半开区间 \([b_j,f_j)\)，因此在时刻 \(f_j\) 释放的资源可以被同刻启动的作业使用。

### 2.3 当前可放置判定

设节点当前空闲 GPU、CPU 为 \(G_n^{free}(t),C_n^{free}(t)\)。同型节点能放置的 worker 数为

\[
q_{jn}(t)=
\min\left(
\left\lfloor\frac{G_n^{free}(t)}{g_j}\right\rfloor,
\left\lfloor\frac{C_n^{free}(t)}{c_j}\right\rfloor
\right).
\]

当 \(c_j=0\) 时忽略 CPU 项；CPU 小数请求保持原值。由于作业内 worker 相同，且题面没有额外网络拓扑或放置亲和约束，在选定 GPU 型号中

\[
\sum_n q_{jn}(t)\ge m_j
\]

即可判定当前存在整体放置方案。节点级容量约束仍需逐项核验，不能用池级 GPU/CPU 总量代替这一条件。

所有策略使用同一个确定性的紧凑放置过程：将 \(q_{jn}>0\) 的节点按 \((q_{jn},G_n^{free},C_n^{free},\text{node\_name})\) 升序排列，依次尽量填入该作业的 worker，直到放满。该规则优先使用对当前作业而言可用槽位较少的节点，尝试保留较大空隙；它不保证最小化所有未来碎片。节点标识符采用字符串字典序，不同调度策略不单独更换放置规则。实现中的 CPU 比较使用 \(10^{-9}\) 的浮点容差，不代表可突破实际容量。

## 3. 第 2 问：三种调度规则

不同 GPU 型号按独立资源池调度。原始题面不存在型号间共享节点，因此分池不会遗漏一个需要跨型号竞争的物理节点。池内只包含已提交且尚未启动的作业。

### 3.1 FCFS

以提交时刻为主键，固定作业标识符为并列键排序。依次启动队首能完整放置的作业；队首不能放置时停止该池本轮调度。该规则易解释，但队首大作业可能使后面的可放置作业继续等待。

### 3.2 Strict SJF

在当前等待集合中按已知运行时长排序，并用提交时刻和作业标识符打破并列。严格按顺序启动，队首不能完整放置时停止该池本轮调度。

这里比较的是**严格 SJF，仍有队首阻塞**，不是“从所有可放置作业中挑最短者”。新到达的短作业可以排到已等待的长作业之前，因此需要报告长作业群体的等待代价。有限数据中的全部作业最终能否完成由仿真核验，不提前宣称出现无限等待或不存在公平性问题。

### 3.3 保护队首的保守回填（CBF-128）

主队列仍按 FCFS。队首可启动时立即启动；队首 \(h\) 被阻塞时，计算其最早可行预约时刻 \(t_h^*\)。

预约只根据当前运行作业的已知完成时间构造：复制当前节点空闲资源，按未来完成事件逐批释放，找到首次满足 \(\sum_n q_{hn}\ge m_h\) 的时刻。这个推算不能读取尚未提交作业，也不能先把节点资源聚合后再做放置。全部作业已通过空集群可行性检查，因此在当前运行作业有限时，预约应该存在；找不到预约属于需报错检查的状态。

取队首之后前 \(L=128\) 个 FCFS 排队位置作为候选集，再按运行时长及确定性并列键尝试。作业 \(j\) 仅在以下两个条件同时满足时回填：

\[
\operatorname{Fit}(j,t)=1,\qquad t+d_j\le t_h^*.
\]

成功启动一个候选后更新实际空闲资源，再检查剩余候选。扫描上限限制的是候选个数，不是运行时长或预约前视时间；不能把超过 128 个排队位置之外的作业描述成已被搜索。

### 3.4 预约保护保证与适用范围

在运行时长准确、资源按时释放、同刻完成先于启动的条件下，每个回填作业在 \(t_h^*\) 前或同刻释放全部资源。因此到了 \(t_h^*\)，原来支持队首启动的节点容量不会因这些回填而减少；已确定的当前队首预约不会被此次回填延迟。

这一保证只针对当前受保护队首的预约，不说明：

- 所有比回填作业更早到达的作业都同时获得保护；
- 与另一条完整 FCFS 仿真相比，每个作业的启动时刻都不变或提前；
- 已覆盖所有安全回填机会；
- 128 个候选足以得到最优结果。

例如，一个持续超过 \(t_h^*\) 但只使用队首不需要节点的作业也可能安全，当前规则仍会拒绝。本文将方法称为 **EASY 思想启发的保守回填**，不等同于完整实现 Slurm，也不等同于为每个排队作业都预约的 classical conservative backfilling。[Slurm 官方调度说明](https://slurm.schedmd.com/sched_config.html)支持“低优先级作业不应推迟受保护作业预计启动时间”的原则，但本文具体候选上限和提前结束条件是本项目的简化设计。

## 4. 统一事件驱动仿真

维护下一次提交事件和运行作业最小完成时间。时钟跳到下一个事件，不逐秒扫描。

同一时刻按以下顺序处理：

1. 批量完成并释放该时刻结束的全部作业，包括迁入作业。
2. 将该时刻所有新到达作业加入各自的原生型号队列。
3. 在受影响的型号池执行选定的原生调度规则，直到该规则无法继续启动。
4. 第 3 问启用时，按第 5 节只检查本次新到达且仍在等待的兼容 A10 作业。
5. 分流移除 A10 等待作业后，再次执行 A10 原生调度，使队首变化及时生效。
6. 记录资源分配、排队状态及新生成的完成事件。

同刻到达与即时分流候选按 `job_name` 字符串字典序处理；各受影响型号池按型号字符串排序调度。每个 job 只有一个状态：未到达、等待、运行或完成；跨型号分流不能复制 job。若已无未来到达和运行完成事件但仍有等待作业，必须作为失败报告，不得静默截断仿真。

第 2 问禁用分流步骤。第 3 问使用与无分流基准相同的原生调度和放置过程，避免把算法切换的收益误认为跨型号灵活性的收益。

## 5. 第 3 问：一次性即时跨型号分流

### 5.1 兼容集合与速度假设

只考虑从 A10 向 A100-SXM4-80GB 或 A800-SXM4-80GB 分流，不新增节点，不做 GPU 切片，不引入价格或用户行为模型。

对每个 A10 作业，用 UTF-8 字符串 `seed:job_name` 计算 SHA-256，取前 8 字节的大端无符号整数除以 \(2^{64}\)，得到资格分数 \(u_j\)。给定兼容比例参数 \(p\)，若 \(u_j<p\)，则将它视为可使用两个目标型号。相同 seed 下，较小 \(p\) 的资格集合嵌套于较大 \(p\) 的集合；不同 seed 改变被选作业，而不是改变其原始字段。

\(p\) 是资格规则的作业比例参数，有限样本的实际资格比例可能略有差异。它不等于符合资格的 GPU 工作量占比，也不等于实际迁移比例。实验应分别记录三者，尤其注意长时作业导致的工作量集中。

实际迁移保持每 worker GPU 数、CPU 数、worker 数不变，采用 1:1 GPU 数量映射。设统一加速参数为 \(a>0\)：

\[
d_j^{exec}=d_j/a\quad\text{（实际迁移时）};\qquad
d_j^{exec}=d_j\quad\text{（仍在原池时）}.
\]

主实验取 \(a=1\) 和 \(a=2\)。这是整体运行时长的假设，不能称为 GPU 型号的实测性能比。CPU 请求数量不变，但占用时间随运行时长一起缩短。允许连续时间，不将半秒等变换后时长随意取整。假设没有额外移植、传输或启动开销，结果的适用边界必须保留这一说明。

### 5.2 只在到达时尝试，不建立迁入等待队列

一个 A10 作业只在它的提交事件中、原生调度结束之后尝试分流。若它已经在 A10 启动，则不迁移；若不符合条件，则继续留在 A10 原生队列，**以后不再尝试跨型号分流**。

这一限制使机制在线且简单，但可能错过稍后目标池释放资源的机会。因此它不能代表所有跨型号策略可获得的最大收益，也不能将未迁移的兼容作业解释成永远不适合目标型号。

### 5.3 原生优先、双资源借用上限与节点可行性

目标池 \(k\) 必须满足：

1. 已完成当前事件的原生调度，且其原生等待队列为空；不是“没有当前能放下的原生作业”，而是确实没有原生等待者。
2. 候选作业现在可以在该型号的节点上完整放置。
3. 接纳后，迁入运行作业占用同时满足 GPU 和 CPU 借用上限。

记该池当前所有迁入运行作业占用为 \(B_k^G(t),B_k^C(t)\)，池容量为 \(G_k^{cap},C_k^{cap}\)，借用比例参数为 \(\beta\)。接纳候选 \(j\) 后要求

\[
B_k^G(t)+G_j\le\beta G_k^{cap},\qquad
B_k^C(t)+C_j\le\beta C_k^{cap}.
\]

等价地，迁入后的 dominant resource share 不超过 \(\beta\)。GPU 用量仍为整数，CPU 可为小数；上限不是把物理 GPU 切成小数份。借用上限只控制该池中同时运行的迁入占用，不是兼容作业数量的上限，也不是整个实验累计可迁移工作量的上限。

原生调度优先和双上限不能证明原生作业零损失。已启动的迁入作业不可抢占，未来原生作业到达后仍可能被它们阻塞；必须通过配对指标量化代价。

### 5.4 A10 GPU 工作量压力与预计完成比较

在当前时刻 \(t\)，将 A10 正在运行作业的剩余 GPU 工作和原生等待作业的完整 GPU 工作相加：

\[
R_A^G(t)=
\sum_{i\in\mathcal R_A(t)}G_i(f_i-t)
+\sum_{i\in\mathcal Q_A(t)}G_id_i.
\]

候选 \(j\) 此时仍在 A10 等待队列内，因此以

\[
\widehat w_{A,j}(t)=
\max\left(0,\frac{R_A^G(t)-G_jd_j}{G_A^{cap}}\right)
\]

作为工作量压力启发式。量纲为秒。扣掉自身工作量，避免直接把候选自己的运行工作也计为排队压力。依次分流时，应使用移除先前成功候选后的当前队列状态更新此量。

仅当目标池立即启动的估计完成时刻更早时才接纳：

\[
t+d_j/a < t+\widehat w_{A,j}(t)+d_j.
\]

这里不是准确的等待时间预测，也不构成作业实际一定更快完成的保证：它把所有其他等待工作放进分子，未建模候选的真实队列位置、短作业回填、不可抢占结构或节点资源碎片；同时只考虑 A10 GPU 压力，未做 CPU 等效等待预测。该指标仅用于决定是否值得尝试即时分流。

若两个目标型号都满足全部条件，按 `(predicted_finish, donor_order)` 选择最小者，固定 donor 顺序为 A100-SXM4-80GB、A800-SXM4-80GB。由于主实验对二者使用统一速度因子，预计完成时刻相同，实际并列时优先 A100。这个顺序是确定性的实现设定，不表示已证明 A100 是更优目标。成功分流时，原子地从 A10 队列移除该作业，并立即提交目标池完整放置；不把它永久改派到另一个等待队列。

## 6. 评价指标与公平比较

### 6.1 全部作业的等待与完成

定义等待、周转和最后完工时间：

\[
w_j=b_j-s_j,\qquad F_j=f_j-s_j,\qquad C_{max}=\max_j f_j.
\]

完整仿真运行到全部作业完成，以全部作业为分母报告平均、中位、P95、最大等待及 \(C_{max}\)。同时按原请求型号、时长组和单/多 worker 分组，检查整体平均是否掩盖长作业或较小群体的代价。没有组织和用户标签时，不宣称已经评价用户级公平性。

第 3 问比较等待和周转时，作业分组始终按原请求型号；实际运行型号另列字段，避免迁移把较困难作业从 A10 统计中移除，造成表观改善。

### 6.2 固定窗口内分配与完成

沿用第 1 问的 \(H=90\times86400\) 秒作为固定评价窗口。定义作业区间与窗口的交叠长度

\[
\ell_j(H)=\max\{0,\min(f_j,H)-\max(b_j,0)\}.
\]

池 \(k\) 的 GPU 分配率为

\[
U_k^G(H)=\frac{\sum_{j:\,actual(j)=k}G_j\ell_j(H)}{HG_k^{cap}},
\]

CPU 按相同方式计算。它是**模拟中已分配资源的时间比例**，不同于第 1 问的无约束立即启动需求，也不是测得的 GPU 核心使用率或硬件算力效率。

报告窗口末已完成数、正在运行数、等待数，并明确边界口径：例如 \(f_j\le H\) 为已完成，\(b_j\le H<f_j\) 为运行，\(b_j>H\) 为等待。全部输入提交均早于 \(H\)，三者必须加总为全体作业数。不能只对窗口内已完成作业报告平均等待并把它当作总体表现。

第 3 问改变执行时长后，更低的分配率可能意味着同样任务使用了更少资源时间，因此不能将分配率下降直接判为性能恶化。应结合等待、周转、完成数量和原生损害解释。

### 6.3 donor 原生损害

用相同的 Q2 原生算法作为无迁移基准。对每个原生 A100/A800 作业按 `job_name` 配对：

\[
\Delta w_j=w_j^{migration}-w_j^{baseline}.
\]

每个 donor 型号分别报告平均和 P95 等待，以及 \(\Delta w_j>0\) 的作业比例、正延迟分布和最大等待增加。若没有受损作业，报告中的正延迟分位数标为无适用样本；当前输出表对此使用数值 0 作为约定，必须结合受损比例解释，不能把空样本当成存在一个零延迟分布。总体平均改善不能代替这一检查；两个策略 P95 的差值也不能代替逐作业的损失分布。

### 6.4 计算成本与分流规模

记录模拟或调度核心的墙钟耗时、候选检查次数、预约次数，说明是否排除了文件读取、绘图和写出。单次墙钟耗时会受机器环境影响，算法工作计数可辅助解释可扩展性。

第 3 问额外报告符合资格作业数、实际迁移数、目标型号、迁移作业原始 GPU 工作量占比，以及实际执行资源时间。资格集合、资源可放置性和即时决策共同决定迁移规模，不能把 \(p\) 直接标为迁移比例。

## 7. 实验矩阵

以下配置预先设定，用于分解机制；不是事后宣布的最佳参数。

### 7.1 Q2 对照与扫描限制

| 运行 | 队列策略 | 候选上限 | 用途 |
|---|---|---:|---|
| Q2-FCFS | FCFS | 不适用 | 可解释的先来先服务基准 |
| Q2-SJF | Strict SJF | 不适用 | 检查短时优先的平均与长尾权衡 |
| Q2-CBF128 | 保护队首的保守回填 | 128 | 主要回填方案 |
| Q2-CBF512 | 相同回填规则 | 512 | 检查更大候选集合是否值得增加计算成本 |

四者使用相同输入、放置规则、事件顺序和评价窗口。若 CBF512 与 CBF128 差异很小，也应如实报告；不能预先写成更大扫描一定更好。

### 7.2 Q3 分流敏感性

主敏感性实验固定原生算法为 Strict SJF，与无迁移的 Q2-SJF 配对，考察在主要目标表现较好的队列规则上继续分流的增量影响。选择主基线不等于宣布 SJF 对全部目标最优；尤其需并列报告最大等待、长时作业尾部等待与最后完工时间。中心设置为 \(p=0.5,a=1,\beta=0.25\)，中心种子为 `20261017`。另加一个 CBF-128 中心分流配置，与无分流 Q2-CBF128 单独配对，检查分流效果对原生队列规则的依赖。

| 实验组 | \(p\)：兼容比例 | \(a\)：速度因子 | \(\beta\)：双资源上限 | 种子 | 目的 |
|---|---|---|---|---|---|
| 无迁移主基准 | 0 | 1 | 不适用 | 不适用 | 复用 Q2-SJF |
| 兼容性主比较 | 0.25、0.5、1 | 1 | 0.25 | 20261017 | 隔离兼容资格增加的作用 |
| 速度敏感性 | 0.5 | 2 | 0.25 | 20261017 | 检查运行时长假设的影响 |
| 保护强度 | 0.5 | 1 | 0.1、0.5 | 20261017 | 观察 A10 收益与 donor 代价的权衡 |
| 资格集合稳健性 | 0.5 | 1 | 0.25 | 20261018、20261019 | 与中心种子组成三个资格样本 |
| 回填中心对照 | 0.5 | 1 | 0.25 | 20261017 | 原生算法改为 CBF-128，仅与 Q2-CBF128 配对 |

中心配置在各组中复用，总计 8 个 SJF 迁移配置加 1 个回填迁移配置，共 9 个 Q3 配置。八个主配置均与无分流 SJF 配对，额外回填配置只与无分流回填配对。不能把“回填无分流→SJF 有分流”的全部差异归为跨型号收益。

没有探索所有参数交互，因而不能据此声称对所有兼容率、速度和保护强度都稳健。三个固定种子提供有限的样本敏感性检查，不是对真实业务兼容性的统计估计。最终建议应同时说明平均等待、完成量和尾部代价；例如长作业平均等待改善与该组 P95 恶化可能同时发生，不能把它概括成所有长作业都更差。

## 8. 验证与证据保存

仿真核心见 [scheduler.py](../src/scheduler.py)。仿真应保存每个作业的原请求型号、实际型号、提交/启动/结束时间、原始/实际时长、迁移资格及状态，并保存能够还原节点占用的放置记录。保留运行参数、种子、输入与脚本哈希，以便结果可复现。

验证分三层进行：

1. **小型边界场景。** 覆盖 CPU 零/小数请求、同刻完成与到达、节点碎片、同时启动、多 worker 整体提交、队首预约不被回填推迟、两个资源借用上限、迁移后不可重复启动，以及到达时失败后不再重试。
2. **独立资源审计。** 从输出重建每个节点的时间事件，检验作业唯一性、\(b_j\ge s_j\)、执行时长、worker 数、型号许可、非抢占和任意时刻双资源容量。审计不依赖主调度器的可行性函数。
3. **指标与来源核对。** Q2 全运行期资源积分应等于原始完整工作量；Q3 应等于按实际执行时长计算的工作量，而不是强行与原工作量一致。全期工作量属于独立审计范围；固定窗口截断和完成/运行/等待口径由评价单元测试覆盖，donor 损害按同一原生作业配对。输入与代码哈希由运行清单记录并另行核对。

独立资源审计不证明队列优先规则或全局最优性，也不独立重算全部固定窗口指标。预约保护和特定事件序依靠针对性单元测试与代码审查；最终报告应区分这些证据层次，不把“资源合法”扩展为“所有算法性质均已证明”。

所有结论必须由完成的仿真与核验支持。尚未运行或失败的配置必须明确标识，不能补写收益比例。AI 协助内容和人工核验要求继续记录在 [项目状态](../CURRENT_STATUS.md)，最终参赛稿按题面要求披露。

## 10. 本轮扩展：aging、持续 pull 与预登记选择

### 10.1 不需更新堆的线性 aging

对已到达作业取优先分数 `d_j - α(t-s_j)`，越小越先执行。相同时刻公共项 `-αt` 可消去，所以按静态键 `(d_j+αs_j,s_j,job_name)` 排序即可，避免每个事件遍历并更新全部等待作业。所有已在等待的作业之间相对顺序不会随时间改变；抗饥饿的效果来自较早的长作业逐渐优于后来到达的短作业，而不是两条已存在作业分数会交叉。队首仍严格阻塞，节点放置规则不变。

α=0 精确回到 SJF。α 很大时提交时间更重要，但相同提交时刻仍优先短作业，因此不声称它与 FCFS 完全等价。α 无量纲，提交与运行时间都使用秒。

在运行前登记 `{0,.001,.003,.01,.03,.1,.3,1,3,10,30,100}`。若存在同时满足最大等待、最后完工时间不劣于旧 FCFS 的点，选择其中平均等待最小者；否则使用三目标非支配集到归一化理想点的距离选择折中方案。具体归一化、平局规则见 [D018](../DECISIONS.md)。这是一条可复现管理规则，不是全局最优证明。另报告相邻参数的结果；同一轨迹上选择并评价参数存在样本内偏好。

### 10.2 事件驱动 pull

维护按 `(submit_time,job_name)` 插入的 A10 资格等待集合。每个事件先释放所有同刻完成，接收所有同刻到达，对受影响原生池调度，再按预定 donor 顺序拉取等待作业。目标池原生队列必须为空；只扫描资格集合最早的 256 个条目，逐个检查等待阈值、逐节点 gang 放置、GPU 和 CPU 双并发借用上限。成功作业立即从 A10 等待集合移除并启动，不经历目标等待队列；本次分流结束后再次调度 A10。

当 τ>0，仍在排队的资格作业在 `submit+τ` 建立独立事件，确保即使没有其他到达或完成也能尝试分流。已启动作业对应的事件惰性作废。该机制只使用已经到达的作业，不偷看未来。pull 不再依赖原版聚合工作量的完成预测；原生优先也不能保护尚未到达的原生作业，因此必须继续量化其代价。

四个主配置依次为：aging+arrival(A100,A800)；aging+pull(A100,A800)；aging+pull(A100,H800,series-2)；aging+pull(A100,H800,series-2,A800)。最后一种 A800 上限为 .1，其余为 .25。默认 p=.5、速度=1、τ=0、种子20261017。以第三个配置为中心改变 p=.25/1、cap=.1/.5、τ=1/6小时、速度=2、种子18/19，并补充去掉匿名型号的 AH 与 SJF 桥接。总计 15 个新增分流仿真和一个无分流基线视图。

### 10.3 donor 代价约束与兼容假设

预设每个 donor 原生作业平均等待增量≤0.5小时、P95等待增量≤2小时，筛选后最大化 A10 平均等待降幅。此处 P95增量是两个原生等待分布的分位数差，不能替代配对正延迟的 P95。速度2、其他种子和 SJF桥接只检查敏感性，不参与主建议选择。另在 donor 全部已命名的配置中单独选型；无合格且有正收益的配置则保留不分流。阈值及排除规则在运行前写入 [D019](../DECISIONS.md)，不是题面提供的服务等级标准。

所有目标型号均是假设应用兼容后的资源情景，显存更大不构成兼容性证据；GPU-series-2 尤其不能映射为已知硬件。p 表示兼容且愿意参与的联合比例；可讨论价格激励增加参与意愿，但数据不足以估计价格弹性、均衡价格、收益或利润。本轮不以真实价格或更高性能作未经验证的补充假设。

### 10.4 精确空闲积分与不均衡

记 `Q_k(t)` 为原请求型号 k 的等待作业总 GPU 请求（半开区间 `[submit,start)`），`I_k(t)` 为物理池 k 的空闲 GPU。迁移作业启动前仍计入 A10 等待。对所有到达、启动和结束的事件网格聚合同刻变化，积分计算：

- 本池排队空闲 `E_k=∫I_k(t)1[Q_k(t)>0]dt`，单位 GPU小时；条件空闲率除以“容量×本池有队列的时长”，无队列时为 null。
- 固定集合 D={A100,A800,H800,series-2} 的 `∫Σ_D I_k(t)1[Q_A10(t)>0]dt`。
- `S=∫min(Σ_D I_k(t),Q_A10(t))dt`。这是当前实现时间线上的瞬时匹配上界，忽略 CPU、兼容性和装箱，不能当作其他重调度方案收益的上界。
- 六池 GPU 分配率最大值减最小值，以及 A10 减去 D 按 GPU 容量加权分配率（有符号）。

主指标均在90天窗口内计算，另保存全清空窗口。窗口间不能混用；分配率只是模拟占用，并非硬件核心利用率。

### 10.5 存储、回归与审计边界

原13份完整输出及其审计保留不变，以新核心重跑并精确比较原有全部调度字段和节点 worker 分配。新主配置完整保存并独立审计，参数扫描默认只保存指标与来源清单；`metrics_only` 条目明确跳过逐节点审计。小型手算测试覆盖 aging0、同刻排序、资格事件、双cap、零CPU、精确积分及配对分位差。审计仍不证明全局最优或全部优先规则；其范围是输出资源与时长合法性，规则性质依靠代码审查和针对性测试。

## 11. v2：分组保护、对数 aging 与迁入占用控制

### 11.1 主选择规则的改变

[D023](../DECISIONS.md) 在新增实验运行前登记，替代D018的主选择部分。候选包含FCFS、SJF、回填128/512、原12个线性aging和6个对数aging。C1要求每个原始时长组 `(0,1h]、(1h,1d]、(1d,7d]、(7d,∞)` 的平均等待不高于FCFS同组值；C2要求总体均值≤2倍SJF精确均值。通过两约束后依次最小化最大等待、总体均值，最终按场景名排序；无可行点回退SJF。保存每个候选每个约束的实际值及判定，不用舍入数筛选。

旧规则α=100保留为严格限制最大等待和清空时间的备选。规则调整由对前轮目标失衡的审查触发，并在新扫描前固定；不能称其为未见过任何数据的独立预注册，也不能把FCFS的极值表现泛化为异质多节点gang调度的最优定理。全流程属于同轨迹样本内选择。

### 11.2 对数 aging 的尺度与实现

取静态键 `k_j=ln(d_j/1秒)+a_j/T`，T∈{1小时,6小时,1天,3天,7天,30天}。时变分数为 `ln(d_j/1秒)−(t−a_j)/T`，相差公共项−t/T，故可复用堆。相同键按提交时间、文本job_name及输入序号打破平局，仍严格队首阻塞。

长作业L早于短作业S提交，当 `a_S−a_L > T ln(d_L/d_S)` 时L优先；多等T能抵消e倍时长差。T=1天、时长100天与1小时的提交间隔临界约7.783天。这描述不同提交间隔下新到达者与旧作业的比较；两个已经同时排队的作业不会只因时钟流逝而改变相对顺序。所有时长仍为已到达作业的已知字段，不使用未来作业。

### 11.3 正式尾部与配对受损诊断

以FCFS为基线严格按job_name对齐并验证原始属性一致。定义 `Δw=w_candidate−w_FCFS`，受损集合为Δw>0，不使用容差；报告受损人数/比例、受损者平均正增量及其原始GPU工作量占全部作业工作量的比例。工作量以原时长×每worker GPU×worker数计算，不以作业数替代。

另对等待>1000小时和>FCFS精确最大等待分别报告人数、原请求型号构成、原时长min/P25/P50/P75/P95/P99/max。空集合的条件均值和分位数为null，计数与工作量比例为0。总体和每个原始时长组计算 `max(1,(end−submit)/max(run_duration,60秒))` 的均值、P99和最大值。P99采用线性插值；其稳定性是相对单个极值而言，不构成样本外保证。

Q2主选择依据四个时长组的均值，不能由组均值保护推出个体零损失。固定90天的GPU工作量、完成作业数与等待分布也不可互换：池饱和不增加物理容量，但不同排序可能改变窗口内完成作业数和实际分配时间。

### 11.4 迁入时长上限与空闲保留

在pull模式增加D_max，只有原时长≤D_max的兼容A10作业才进入可拉取集合；默认None不限制。超时长作业的 `flexible=True` 保留，以区分技术/参与资格和时长可拉取资格。过滤必须在进入集合前完成，避免前256个长作业耗尽扫描前缀，遮住后续短作业。

每次迁入前检查 `free_GPU−job_GPU≥R×pool_GPU` 与CPU对应条件，等号允许。默认R=0保持旧行为；只在当前迁入启动后要求汇总空闲比例，不把预留视为永久闲置，后续或同刻稍后启动的原生作业可使用它。池级余量不保证特定节点的可放置性，因此仍执行原逐节点gang放置和借用上限检查。两字段在arrival模式忽略。

审计从节点分配重建池级资源：同刻先释放全部完成，再按 `start_sequence` 逐个启动；在每个迁入启动后独立检查CPU/GPU保留界。这样不会错误地要求一批原生作业启动后还必须留足R，也不会漏掉同刻多次迁入逐步耗尽余量的违规。

### 11.5 v2 网格与命名优先

原生均值增量≤.5小时、边际P95增量≤2小时的标准不变，且对每个donor分别检查。主推荐仅从命名型号可行正收益方案中最大化A10均值下降；匿名候选单独选条件性结果。无合格命名点则主推荐不分流，并明确敏感性锚点只是诊断对象。

### 12.1 固定网格与双推荐

严格推荐仍要求每个donor的原生均值增量≤.5小时、边际P95增量≤2小时。补偿推荐需管理层采用积分机制，要求交换比≥100、每个donor均值增量≤1小时、每个donor等待增加比例≤20%。两个规则各自最大化A10平均等待下降，平局按名称；补偿无可行者沿用严格推荐。比例按每池检查，避免大池稀释小池损失；汇总比例另报。阈值是管理假设，运行后不调整，补偿推荐不替换严格推荐。

对两推荐分别改变种子18/19和p=.25/1，相同推荐去重；所有敏感性均排除选型。v3主实验统一与Q2*无分流配对，保留的旧SJF桥接仍与SJF比较，不混入前沿或选型。

### 12.2 作业小时与GPU加权延迟总账

记δ_j=w_j(new)−w_j(base)，以小时计。A10净节省B=−Σ_A10 δ_j；donor原生正代价H=Σ_native max(0,δ_j)。交换比E=B/H，H=0时按任务约定语义为无穷，JSON为null、CSV为空并带 `exchange_ratio_infinite=True`；选择仍另外要求B>0。不能把净donor均值差乘人数当作正延迟总账，因为前者允许收益抵消损失。

原生受损定义为δ_j>0，直接按同作业ID与原始属性配对；分布P95之差与正配对增量的P95是不同统计量。A10也报告δ_j>0的比例及最大正增量：严格队首阻塞和资源装箱会使移走部分作业改变后续启动顺序，因此源池个体等待不具有单调改善保证。

设g_j=每worker GPU请求×worker数，积分C=Σ_native max(0,δ_j)g_j，A10加权净节省S=−Σ_A10 δ_j g_j，单位GPU小时。C/S仅在S>0时定义；S≤0保存空值并标记未定义。只有统一积分计量并执行转移时，C对应名义延迟积分补偿；它不是实际退款、用户效用或未来优先级反馈的模型。价格和支付意愿缺失，因此不杜撰货币价格或利润。

### 12.3 实际借用峰值

按每个迁入作业完整的[start,end)区间，分别累计总GPU与总CPU占用；同刻先释放，再启动，CPU使用Decimal累加。GPU和CPU峰值可以发生在不同时刻，不能将二者拼成一个真实同时状态。峰值按全部仿真窗口统计，不限90天；其占对应donor总容量的比例用于解释实际承接者和限制是否触及，不等同平均利用率。
